## 提问结束后，不应该再多一道整理任务

在学习编程时，我希望带着代码和上下文直接提问，并自然地留下可以回看的知识。但早期界面仍需要手动点击“整理这条对话”：提问已经完成，工具却又要求我决定是否整理、等待生成，再管理记录。

这个阻力决定了后来的设计方向：知识整理应当是学习的后台过程。主动性体现在替用户承担可以自动完成的工作。

## 先展示完整回答，再自动后台整理

| 方案 | 好处 | 代价 |
| --- | --- | --- |
| 手动整理 | 调用可控 | 多一步操作，也容易遗漏 |
| 与回答一起等待 | 结果一次齐全 | 整理耗时进入学习等待 |
| 完整回答后后台整理 | 学习继续，卡片随后出现 | 系统需要处理失败、重试与恢复 |

我选择第三种。完整真实回答结束后，先保留问答，再安排知识卡生成。前台的新对话拥有更高优先级，后台整理等待合适时机。自动标题复用整理请求，减少一次额外调用。

## 把生成能力接到可管理的执行流程里

VS Code Webview 负责交互，扩展侧处理模型请求和本地状态。后台队列把原始问答转换成结构化知识卡，再同步到学习日志。生成失败时保留原始记录，结合有限重试、退避与重启恢复。

跨会话记忆从当前工作区检索最多三张已确认的相关知识卡；用户修改和删除卡片后，检索结果也随之变化。知识卡保留原始来源，自动化产出仍然可以修正。

## 自动出现只是起点，读起来方便同样重要

实际使用中，自动整理减少了操作，但有些按钮仍不方便，部分知识卡过长。我把不同知识点拆为胶囊按钮，把例子、理解检查与原始问答做成可折叠内容：先看到核心概念，再按需要展开。

这是根据个人使用反馈做出的交互迭代。目前没有量化的学习效果实验，因此我将它描述为操作与阅读体验的改进。

## 区分工程检查与学习效果

项目 README 记录了 94 项离线工程测试与 12 个合成记忆回归案例。它们为行为回归提供依据，不代表模型回答质量或实际学习效果已经得到全面评估。本次博客改版没有重新运行项目测试。

“懂了”是一种用户自评，记录确认也不等于掌握。项目保留编辑、删除与来源追溯，真正的掌握验证、间隔复习与完整记忆压缩尚未实现。
